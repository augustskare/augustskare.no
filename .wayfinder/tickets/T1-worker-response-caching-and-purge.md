## Question

This is the linchpin of the whole design. The plan is: the Worker renders `/bookshelf` HTML,
that HTML is cached at the edge for a very long time, and the only refresh lever is clicking
**Purge Everything** in the Cloudflare dashboard. There is no KV and no database, so there is
no second copy of the render anywhere.

If Worker-generated HTML does not land in a layer that the dashboard button clears, the design
does not work.

Establish, from Cloudflare's primary docs:

1. Are responses **generated by a Worker** (not proxied via `fetch` to an origin) stored in the
   zone CDN cache purely on the strength of a `Cache-Control: public, s-maxage=…` response
   header? Or does that require a **Cache Rule**, or an explicit `caches.default.put()`?
2. Does dashboard **Purge Everything** clear:
   - the zone CDN cache? (assumed yes)
   - entries written via the classic Cache API (`caches.default`)?
   - the newer Workers Cache reached by `ctx.cache` / `cache` from `cloudflare:workers`?
     The docs contradict each other here — `workers/reference/how-the-cache-works` lists Purge
     Everything as a way to clear Cache API assets, while `workers/cache/purge` states that
     zone-level purge does **not** affect Workers Caching content. Determine which applies to
     which product, and cite the source for each.
3. Is the classic Cache API (`caches.default`) the same store as the zone CDN cache, or distinct?
   `workers/runtime-apis/cache` says it "differs from Cloudflare's Global CDN".
4. What is the **recommended pattern** for "render once, serve from the edge indefinitely, purge
   by hand from the dashboard" on a **Free plan** custom domain? Note any Free-plan limits.
5. Confirm `cache.delete()` is data-center-local (a known trap) and therefore useless as a
   refresh mechanism here.

Output a recommendation naming exactly one cache layer to use, the response headers to set,
and the evidence that the dashboard button clears that layer.

Answer feeds directly into "Pin the caching contract" (T7) and the cutover runbook (T8).

## Resolution

**The design works — provisionally.** Full evidence with verbatim doc quotes:
[`research/T1-worker-response-caching-and-purge.md`](../research/T1-worker-response-caching-and-purge.md).

**Use the classic Cache API, `caches.default`, with an explicit `cache.put()`.** It is the only
layer that holds a Worker-_generated_ response, needs no storage product, and is documented as
cleared by dashboard Purge Everything. Headers: `Cache-Control: public, max-age=60,
s-maxage=31536000` plus `Cache-Tag: bookshelf`. No Cache Rule, no Wrangler cache config.

1. **A `Cache-Control` header alone does nothing.** Workers "execute after the caching decision
   has been made"; the zone cache sits behind the Worker, not in front. A Cache Rule cannot help
   either — it matches the Worker's `fetch()` subrequest, and with the HTML rendered in-Worker
   there is no subrequest. An explicit `cache.put()` is mandatory.
2. **Purge Everything clears Cache API entries** — and does _not_ touch Workers Cache.
3. **The doc contradiction was two products, not an error.** The classic Cache API
   (`caches.default`, always available, explicit `put`, zone-scoped, purgeable) is distinct from
   the newer opt-in Workers Cache (`ctx.cache`, header-driven, zoneless, immune to zone purge).
   Both doc pages are correct about their own product.
4. **`cache.delete()` is data-center-local** — confirmed useless as a refresh lever.

### Consequences that change other tickets

- **Cache API only works on a custom domain.** Dashboard-editor and Playground previews have no
  functional cache. So the caching behaviour **cannot be verified on a `workers.dev` URL** — which
  breaks T8's assumption that everything is provable before the apex is touched. Suggested fix,
  for T8 to decide: attach the Worker to a throwaway custom domain on the same zone
  (e.g. `shelf-test.augustskare.no`), which gives a real zone-scoped cache to test the full
  render → hit → purge → re-render loop against, with the apex untouched.
- **"Render once" is false.** Cache API entries do not replicate between data centers, so the page
  renders once _per data center that sees traffic_; and `s-maxage` is an LRU ceiling with no
  documented retention floor, so an unpopular page gets evicted and re-rendered at unpredictable
  intervals. T7 must not promise otherwise.
- **Keep `max-age` short (60s).** A long browser TTL makes Purge Everything look broken to
  returning visitors, who keep serving their own copy.
- **Purge-by-URL is not confirmed** for Cache API entries; only Purge Everything and purge-by-tag
  are affirmed. Hence the `Cache-Tag`.

### The load-bearing risk

The whole design rests on **one sentence** in Cloudflare's docs, in a paragraph that hedges "not
all cache purge endpoints function" for Cache API assets. It is current and canonical, but
singular. Treat the design as provisional until the empirical test passes: render, curl twice for
an identical response, Purge Everything, curl again and confirm it changed.

**If it fails**, the fallback is Workers Cache (`ctx.cache`) plus a secret purge route — which
T1 notes is technically the better cache anyway (read-through, tiered, request-collapsing), and
costs only the refresh lever changing from a dashboard click to opening a bookmarked URL.
